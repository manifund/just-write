@AGENTS.md

## What this is

Site and member portal for [justwrite.club](https://justwrite.club), a November 2026 online writing club run by Austin through Manifund. Writers express interest, sign in, sign terms, and pay a $1,000 deposit (refunded if they publish 4 essays); committed writers get the member portal. Next.js 16 App Router + Tailwind v4, Convex (data, realtime, auth via Better Auth), Stripe, Resend, OpenRouter. Deployed on Vercel (manifund team, `just-write` project); pushes to `main` deploy to production. `MUSINGS.md` has (old) program notes; `just-write-handoff/` has the approved landing design.

## Commands

```bash
bun install
vercel env pull .env.local   # Stripe keys etc. (bun auto-loads .env.local); then `bun convex` to restore CONVEX_DEPLOYMENT
bun convex                   # pushes convex/ to the dev deployment and watches; tails Convex logs
bun dev                      # localhost:3000
bun check                    # Bun's built-in typechecker (same errors as tsc; includes convex/)
bun lint                     # eslint on app lib components convex scripts (bare `bunx eslint` also scans .next and reports bogus errors)
bunx convex run chat:seedChannels  # create/update the default chat channels (once per deployment)
```

Use `bun` and `bunx` for everything, never `npm` or `npx`. There are no tests.

## Architecture

**Data lives in Convex** (`convex/schema.ts`). `members` (keyed by lowercase `email`) replaces the old Neon `interest` table; its `status` moves `interested → signed → committed`. Other tables: `essays`, `ideas`/`ideaVotes`, chat (`channels`, `messages`, `reactions`, `typing`, `reads`), and `similar` (cached LLM matches). Schema changes deploy with the Convex functions; no migrations needed for new optional fields. `scripts/import-neon.ts` is the one-time copy from Neon.

**Auth:** Better Auth runs inside Convex (`convex/auth.ts`, Google + email magic link); `app/api/auth/[...all]` proxies to it so cookies stay on our domain. A signed-in user is matched to their `members` row by email (`convex/lib/viewer.ts#getViewer`), or by the row's optional `altEmail` (a second sign-in address, set with `bunx convex run members:setAltEmail`). Committed members and `ADMIN_EMAILS` can use the portal; every Convex function checks this itself (`requireMember`, `requireAdmin`), so the client-side gate in `components/portal/frame.tsx` is only UX. Next.js server code calls Convex as the user with `fetchAuthMutation` (`lib/auth-server.ts`), or calls `convex/server.ts` functions with the shared `CONVEX_SERVER_SECRET`.

**Flow:**

1. `/` — `app/(site)/actions.ts#submitInterest` calls `members.expressInterest`. The public "Interested" list (`app/(site)/interested.tsx`) is a `"use cache"` function tagged `interest`; anything that changes who appears there must invalidate that tag (`updateTag` in server actions, `revalidateTag(..., { expire: 0 })` in route handlers).
2. `/commit` — requires sign-in. `app/(site)/commit/actions.ts#startCommitment` records the signature on the viewer's row (`members.signTerms`, status `signed`) and redirects to Stripe Checkout with the Convex member id as `client_reference_id`.
3. `app/api/stripe/webhook/route.ts` — on `checkout.session.completed` / `async_payment_succeeded`, `markCommitted` (`lib/stripe.ts` → `server.markCommitted`) flips the row to `committed` (numeric references are pre-Convex Neon ids, matched via `legacyId`), then `sendSignedTerms` (`lib/email.ts`) emails the signed terms. Both are idempotent, and failures return 500 so Stripe retries. `/commit/thanks` only displays Stripe's session status; the webhook is the source of truth.
4. Portal (`app/(portal)/`, client-rendered behind `PortalFrame`): its layout is a second root layout that turns the session cookie into a Convex token server-side and hands it to `PortalProviders` in `app/providers.tsx`, so the browser connects already signed in. Member-only pages are in `app/(portal)/(private)/`; `/members` and `/calendar` are public but sit in the same root layout so sidebar navigation stays client-side. The landing page, `/sign-in`, `/commit`, and `/tweaks` live under `app/(site)/` with a static root layout and Better Auth's own provider; crossing between the two groups is a full page load. Pages: `/home` (deadline countdown, essay slots, registering essays, similar writers, everyone's progress), `/chat/[slug]` (channels with threads, reactions, typing, presence, unread dots), `/ideas`, `/settings` (profile), `/admin` (admins only; essay review), `/improvements` (every @Claude run).
5. `/members` and `/members/[handle]` — public, server-rendered from Convex then live (`app/(portal)/members`); members see them inside the portal shell.

**Essay deadlines** are in `convex/lib/program.ts` (Mondays 9pm PT, Nov 9–30). `fillSlots` assigns registered essays to the earliest open slot they beat; admins can mark essays rejected so they don't count. Registering an essay posts it to `#published`.

**Calendar** (`/calendar`, public; `app/(portal)/calendar`, `convex/events.ts`): each session has its own URL, `/calendar/<slug>` (the calendar with that session's panel open; slugs are set at creation and survive renames). sessions have an owner plus co-hosts (committed members), who can edit, cancel, or hand them off; admins can edit anything. Any member can propose a session, and it goes live right away and is announced in `#meetups` (changes are posted as replies). Addresses and call links are only returned to members. Times are stored as UTC and always shown and entered in Pacific time (`convex/lib/time.ts`). `kind: "deadline"` events mark the Monday deadlines (no RSVPs). RSVPs (yes/maybe/no) are public; the `claimReminders` cron emails yes/maybe RSVPs and hosts about 24h before. Google Calendar: `convex/gcal.ts` mirrors every event into one shared Google calendar through a service account (Convex env `GOOGLE_SERVICE_ACCOUNT_KEY`, `GOOGLE_CALENDAR_ID`; no-ops while unset) and shares it with each member's emails when they commit (`gcal:shareAll` backfills). Other apps use a per-member iCal feed served at `<convex site>/calendar.ics?token=` (`convex/http.ts`). Seed with `bunx convex run events:seed '{"hostEmail": "..."}'`.

**Chat messages** are Tiptap JSON. `convex/lib/richtext.ts#cleanBody` whitelists node and mark types on the server; `components/portal/rich-text.tsx` renders them to React (no raw HTML). The composer is `components/portal/composer.tsx` (Enter sends, @mentions). Switching channels and opening threads change the URL through `lib/chat-url.ts` (the browser's own History methods, read back with `useChatUrl`), never `history.pushState` or the router: Next.js turns pushState into a cache-only restore that can hang for good.

**Installed app and push:** `app/manifest.ts` makes the site installable. It opens on `/home`, its icons are in `public/icons` (rendered from `app/icon.svg`), and links shared to it prefill the essay form. `public/sw.js` only handles push; it caches nothing. Members turn notifications on per device in `/settings` (`lib/push.ts`). Everything that posts a chat message goes through `convex/lib/messages.ts#postMessage`, which schedules `pushAction.notify`, and `push.recipients` picks who gets one: people mentioned and people in the thread, plus every top-level post for members who chose "All new messages". The author and anyone with that channel open (presence) are skipped, and #check-ins text stays behind its gate, as in the app. On iPhone, push only works after adding the site to the Home Screen.

**Activity** (`/activity`, `convex/activity.ts`): mentions of the viewer and replies in threads they're in. Items are `activity` rows (one per member a message involves) written when the message is posted: `convex/lib/messages.ts#postMessage` calls `convex/lib/activity.ts#recordActivity`, which uses the same `involvement` sets as push notifications. Deleting a message drops its rows (`forgetActivity`). Claude's status card is posted empty, so it becomes an item when its run ends (`improvements.endRun`, which every final status goes through). Reading an item sets `readAt`; the sidebar subscribes only to `activity.unreadCount`, and the full `feed` is subscribed on the page itself. Keep it that way: anything the whole portal subscribes to re-runs for every member on every change to what it read, so it should read a few rows of that member's own, never scan messages.

**Similar writers:** `convex/similarAction.ts` asks Claude (via OpenRouter) to pick 3 matches from bios, essay titles, and shared ideas; results are cached in `similar` and recomputed when the inputs' hash changes or after 24h.

**@Claude improvements:** mentioning `@Claude` in chat asks an agent to change this site. Claude is a `members` row with `bot: true` (`CLAUDE_EMAIL`, created by `chat:seedChannels`), in the roster but hidden from directories. `chat.send` → `improvements.startFromMessage` records an `improvements` row, posts Claude's reply in the thread (a message with `improvementId`, rendered by `components/portal/improvement.tsx` as a live checklist, then the result), and schedules `improvements.kick`, which POSTs to `IMPROVE_URL` (`app/api/improve/route.ts`). The route claims the run and starts a Vercel Sandbox with the repo cloned at `/vercel/just-write`, then launches `scripts/improve-runner.ts` detached. The runner runs the Claude Agent SDK (Opus via OpenRouter's Anthropic endpoint), typechecks and lints (giving the agent two tries to fix failures), and reports its steps to `convex/runner.ts`. Then it sends its list of changed files back to the route, and `lib/improve-finish.ts` reads them out of the sandbox, commits them to `claude/<n>` through GitHub's API, opens a PR, and merges it if `MERGE_POLICY` allows (judged on GitHub's diff of the branch, not on what the sandbox says). The sandbox never gets `GITHUB_TOKEN` or `CONVEX_SERVER_SECRET`, since members steer the agent in it: only the OpenRouter key and a random per-run key (Convex keeps its hash in `runTokenHash`) that works for that run's card while it's going and is retired when it finishes. The route runs the runner from the deployed commit (copied to `/tmp/improve-runner`), not the clone's copy. Keep secrets out of the sandbox. Settings (merge policy, models, rate limits, paths that always need review) are in `convex/lib/improve.ts`. Admins get Merge/Close/Revert on the card (`app/(portal)/(private)/improvements/actions.ts`, via `lib/github.ts`). A reply with `@Claude` in the same thread may continue one of the thread's open PRs: before the sandbox starts, the route asks `lib/improve-target.ts#pickTarget` ("new PR" or "#40" in the request wins, then a quick classifier call over the thread, falling back to the previous run's PR) and `server.continuePr` moves the run onto that branch. If the thread's previous run failed after its sandbox started (out of steps, timed out), a reply picks that run up instead, unless it names a PR or asks for a new one: same branch, so its saved sandbox comes back with the uncommitted edits, and the agent session resumes (the runner saves the session id as soon as the agent starts). If the sandbox comes back fresh, it starts over on the branch. When the agent runs out of steps with files changed, the runner still checks and pushes them, and the PR opens marked "(unfinished)" and never merges on its own; the title loses the mark once a follow-up finishes. One sent while a run is still going waits (`waitingOn`). While the agent is working, the runner polls `server.claimFollowUps` and passes those to it at priority `next` (read after its current tool call). Any that arrive after the agent has finished start as their own run when that run ends (`improvements.releaseWaiting`). The member who asked and admins see a Stop button on a running card (`improvements.stop`): a queued run or a chat task ends right away; a code run's runner sees it on its next `runner.followUps` poll, aborts the agent, and goes down the out-of-steps path (edits pushed as an "(unfinished)" PR, or a failed run if nothing changed, either way resumable with "@Claude continue"); `improvements.forceStop` ends it after 90s if the runner doesn't. Writing `effort: high` (low/medium/high/xhigh/max) in a request sets the agent's effort for that run (`convex/lib/improve.ts#parseEffort`). The resolved effort is saved on the run (`effort`), and a follow-up that continues a run (`server.continuePr`) keeps that run's effort unless it sets its own. Merges are announced in `#site`; `/improvements` lists every run. Runs are member-only: `improvements.list` and `improvements.card` call `requireMember` (read-only previews allowed), and the page is in `(private)`, since requests and errors can quote anything said in chat. Smoke-test the sandbox side with `bun scripts/improve-try.ts "<request>"` (dry run: nothing is pushed or reported). The agent returns a structured result (`title`, a 1–2 sentence `chat` reply for the card, and `details` for the PR body).

**@Claude chat tasks** (`convex/chatTasks.ts`): a request that says "chat task" (or follows only chat tasks in its thread, without "new PR"/"PR 40"/"continue #40") reads the club's data instead of changing code, to answer a question or post one message. `kind: "chat"` is set when the run is created (`convex/lib/improve.ts#isChatTask`; `CHAT_TASKS_ENABLED` turns it off). Chat tasks and code runs never wait for or take follow-ups from each other. The route reads `chatTasks.snapshot`/`messages` with the server secret and the run's key (only before its sandbox exists), then starts a throwaway sandbox: bun, the Agent SDK (into `/tmp/agent`), and the runner go in first (`lib/chat-task-sandbox.ts#SETUP`), then a firewall that only lets through the model API on its messages path (the firewall adds the OpenRouter key; the sandbox has a placeholder), the Convex host, and GET/HEAD to any other site (so the agent has WebSearch and WebFetch; a confused agent could leak members-only data in a URL, which admins accepted), then the data at `/tmp/club` and the run key. The runner reports steps through `runner.report` and its result through `chatTasks.finish` (it can't reach `/api/improve`); Convex stops the sandbox when the run ends (the route's `stop` request). The data is what any member sees, never emails, payments, or settings, and never #check-ins text (only who, when, and length); thread briefs for both kinds also reduce check-ins to that, and code-run briefs leave out chat tasks' results, since PRs are public. If the agent returns a post, `finish` posts it as Claude (`messages.postedFrom`, shown with "Posted for <name>", deletable by that member) in one of `CHAT_POST_CHANNELS` (never #check-ins), within `CHAT_POSTS_PER_MEMBER`/`CHAT_POSTS_PER_DAY`; otherwise it stays on the card as a draft with "Use this draft", which adds it to the viewer's own message box (`composer.tsx#addToComposer`). Posts are a Markdown subset converted by `convex/lib/markdown.ts` and cleaned by `cleanBody`. Smoke-test with `bun scripts/improve-try.ts --chat "<request>"` (made-up data, same firewall, dry run).

**Terms text lives in `lib/terms.ts`** as plain data (strings, or runs with links). Both the `/commit` page and the email render from it, so edit terms there, not in JSX.

**Styling:** design tokens (colors `ink`, `cream`, `brass*`; fonts `font-display`, `font-body`) are defined in `app/globals.css`. `/tweaks` is a design playground for fonts and palettes; `app/(site)/tweaks/options.ts` `DEFAULTS` mirrors what the live site uses. The email in `lib/email.ts` hardcodes the same hex colors inline.

**Env vars (Vercel / `.env.local`):** `NEXT_PUBLIC_CONVEX_URL`, `NEXT_PUBLIC_CONVEX_SITE_URL`, `CONVEX_SERVER_SECRET`, `STRIPE_SECRET_KEY`, `STRIPE_PRICE_ID`, `STRIPE_WEBHOOK_SECRET` (live Stripe keys are Production-only on Vercel), `RESEND_API_KEY`, `GITHUB_TOKEN` (repo contents + pull requests write, for @Claude), `OPENROUTER_API_KEY` (passed into the @Claude sandbox), optional `RESEND_FROM` (defaults to `austin@manifund.org`, verified in Manifund's Resend account). Stripe is Manifund's live account; deposits are donations to Manifund. `DATABASE_URL` (Neon) is only used by `scripts/import-neon.ts`.

**Env vars (Convex deployment, `bunx convex env set`):** `SITE_URL`, `BETTER_AUTH_SECRET`, `CONVEX_SERVER_SECRET` (same value as in Vercel), `ADMIN_EMAILS` (comma-separated), `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (Google Cloud project `just-write-513304`; copies kept in gitignored `.env`), `RESEND_API_KEY` (magic links; without it links are logged instead of sent), `OPENROUTER_API_KEY`, `IMPROVE_URL` (e.g. `https://justwrite.club/api/improve`; while unset, Claude replies that it isn't switched on). All are set on the dev deployment (`brilliant-starling-517`), which sends real email. `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` are the key pair that identifies this site to browsers' push services. Generate them once with `bunx web-push generate-vapid-keys` (free, no account). Until both are set, push is off and `/settings` says so. Keep the same keys: subscriptions are tied to the public key, so changing them stops notifications for everyone until each person turns them off and on again.

**One Convex deployment:** there is no production Convex deployment; justwrite.club and localhost both use the dev deployment (`brilliant-starling-517`). So `bun convex` pushes go live immediately, and test data is visible to real members; don't seed fake members or post test messages there. Auth takes its base URL from the request host: `ORIGINS` in `convex/auth.ts` (localhost:3000, justwrite.club) plus this project's `just-write-*-manifund.vercel.app` previews, which `trustedOrigins` allows per request because the Convex proxy only trusts exact hosts. Google sign-in on a preview detours through justwrite.club (Better Auth's `oAuthProxy`), since Google's redirect URIs are fixed; add a host to `ORIGINS` (and to the Google OAuth redirect URIs) to serve auth anywhere else.

**Read-only previews:** the Preview button on an @Claude card goes to `app/(portal)/(private)/improvements/[id]/preview`, which makes a one-time token (`convex/previewAccess.ts`) and redirects to the preview's `/api/auth/preview-access`. That endpoint (in `convex/auth.ts`) signs the member in as themselves with a session marked read-only; its JWT carries `readonly: true`. `requireMember`/`requireAdmin` refuse read-only sessions in mutations (`allowReadonly` exempts presence and read markers), so previews of unreviewed code can't change live data. Vercel has `NEXT_PUBLIC_CONVEX_URL`/`NEXT_PUBLIC_CONVEX_SITE_URL` (all environments) and `CONVEX_SERVER_SECRET` (Production, Development) pointing at it; Production builds on Vercel push `convex/` before building the site (`buildCommand` in `vercel.json`, authenticated by the `CONVEX_DEPLOY_KEY` env var, Production only), so merging to `main` deploys the backend too; preview builds don't push it.
